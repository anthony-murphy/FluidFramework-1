# Schema Package Instructions

## Package Stability

This package is `@alpha @legacy` - **backwards compatibility is NOT required**.

- Breaking changes are allowed without deprecation periods
- Feel free to refactor APIs, rename types, or restructure as needed
- Focus on getting the design right, not preserving old patterns

## Key Documents

- `docs/notes.md` - Active task list, open questions, bugs to fix
- `docs/view-typing-design.md` - Type system design decisions
- `docs/archive/` - Historical design documents
- `README.md` - User-facing documentation and usage examples

**Always check `docs/notes.md` for:**
- Current task status and priorities
- Known bugs and issues
- Design decisions already made

## Development Workflow

**For each change:**
1. Build after every change: `npm run build`
2. Fix errors before proceeding - don't leave broken builds
3. Run tests: `npm test`
4. Update task status in `docs/notes.md`

**Task status markers:**
- `[ ]` → `[CODED]` - Implementation written
- `[CODED]` → `[BUILT]` - Compiles without errors
- `[BUILT]` → `[TESTED]` - Tests pass
- `[TESTED]` → `[DONE]` - Complete
- `[SKIP]` - Skipped with reason noted

## Don't Hide Bugs

**Never silently work around bugs.** If something is broken, document it clearly.

**Acceptable (with documentation):**
- Suppress an error IF accompanied by a `// BUG:` comment explaining the issue
- Skip a test IF it documents the expected behavior and why it's skipped
- Cast a type IF the comment explains what the correct type should be

**Not acceptable:**
- Casts, suppressions, or skips without clear documentation
- Changing validation logic to avoid incorrect results
- Loose assertions that hide failures

**Always include:**
- `// BUG:` comment explaining what's wrong
- `// TODO:` with what needs to be fixed
- Document significant issues in `docs/notes.md`

```typescript
// BUG: Type inference returns `unknown` instead of `string` for map values
// TODO: Fix InferMapValueType to properly extract value type
// eslint-disable-next-line @typescript-eslint/no-unsafe-assignment
const value = view.get("key"); // Currently: unknown, Expected: string
```

## Design Alignment with SharedTree

**Always explore `@fluidframework/tree` (SharedTree) when designing or implementing features.**

This package provides schema-based typing for any DDS (SharedMap, SharedDirectory, etc.) using the same patterns as SharedTree. The key differences:

- **SharedTree**: Schema + Storage tightly coupled in one DDS
- **Schema package**: Schema layer is pluggable, works with any DDS that implements `ISchemaStorage`

**What to align:**
- Type inference patterns (`NodeFromSchema`, `TypeFromField`, etc.)
- Schema factory API (`SchemaFactory`, `sf.object()`, `sf.map()`, etc.)
- Field schema patterns (`sf.required()`, `sf.optional()`)
- Naming conventions for types and APIs

**Where to look:**
- `packages/dds/tree/src/simple-tree/` - Schema factory, type inference
- `packages/dds/tree/src/core/schema-stored/` - Schema definitions
- `packages/dds/tree/api-report/` - Public API surface

## Release Tags & Export Minimization

**Minimize exports at every layer.** Only export what is absolutely necessary.

| Layer | Tag | What belongs here |
|-------|-----|-------------------|
| Public | `@alpha @legacy` | User-facing types only (SchemaFactory, view types, schema types) |
| Internal | `@internal` | DDS-author APIs only (ISchemaStorage, ISchemaPersistence, adapters) |
| Un-exported | (no tag) | Everything else - implementation details, helpers, utilities |

**Guidelines:**
- Default to un-exported. Only add exports when there's a clear consumer.
- `@alpha @legacy` APIs cannot reference `@internal` types (API-extractor enforces this)
- If a type is only used within this package, don't export it
- If a type is only needed by DDS authors (SharedMap internals), use `@internal`
